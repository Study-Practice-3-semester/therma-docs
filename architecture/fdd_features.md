# Структура фичей
**Методология:** Feature-Driven Development (FDD)
**Проект:** Интеллектуальная система рекомендаций по управлению воздухонагревателями (ЕвразТехника)

В данном документе представлена декомпозиция системы на предметные области, наборы функций и конкретные функции.

---
## 1. Область: Симуляция физических процессов
*Ответственный: Глеб*
*Цель: Обеспечить генерацию реалистичных потоков данных (телеметрии) для тестирования системы и демонстрации UI при отсутствии реальных ПЛК.*

### Feature Set 1.1: Управление циклом симуляции
*   **F.1.1.1** Запуск бесконечного цикла генерации данных по выбранному сценарию (норма, авария, обрыв связи).
*   **F.1.1.2** Остановка работающего сценария симуляции.
*   **F.1.1.3** Динамическая смена фазы каупера (Нагрев -> Изоляция -> Дутье) по внутреннему таймеру модели.

### Feature Set 1.2: Математическая генерация телеметрии
*   **F.1.2.1** Расчет кривой роста температуры купола (`dome_temp`) в фазе нагрева на основе функции от расхода газа.
*   **F.1.2.2** Расчет кривой роста температуры дымовых газов (`flue_gas_temp`) с учетом тепловой инерции насадки.
*   **F.1.2.3** Расчет падения температуры горячего дутья (`hot_blast_temp`) в фазе дутья.
*   **F.1.2.4** Наложение программируемого шума (random variance) на все генерируемые метрики для имитации реальных датчиков.

## 2. Область: Экспертная система рекомендаций
*Ответственный: Вика*
*Цель: Анализ поступающей телеметрии в реальном времени, выявление нештатных ситуаций и генерация подсказок для оператора.*

### Feature Set 2.1: Анализ безопасности каупера (Критические инциденты)
*   **F.2.1.1** Выявление превышения порога плавления огнеупора купола (>1350 °C) и генерация CRITICAL алерта на срез газа.
*   **F.2.1.2** Выявление перегрева под-насадочного устройства (температура дыма >350 °C) и генерация алерта на остановку нагрева.

### Feature Set 2.2: Оптимизация процесса горения
*   **F.2.2.1** Анализ соотношения расхода воздуха и газа для выявления химического недожога.
*   **F.2.2.2** Генерация INFO-рекомендации по коррекции коэффициента избытка воздуха.

### Feature Set 2.3: Контроль качества дутья
*   **F.2.3.1** Определение момента, когда каупер исчерпал тепловую емкость (температура дутья падает ниже заданного технологом уровня).
*   **F.2.3.2** Формирование рекомендации на начало перекидки (смену работающего каупера на резервный/нагретый).

### Feature Set 2.4: Поддержка принятия решений и контроль данных
- **F.2.4.1** Контроль актуальности телеметрии: выявление пропуска данных (отсутствие точек более N секунд) и перевод ядра в режим «Недостаточно данных» (блокировка генерации новых алертов).
- **F.2.4.2** Расчет ожидаемого эффекта: вычисление прогнозируемой дельты температуры дутья и расхода газа для каждой сформированной рекомендации.
- **F.2.4.3** Формирование структурированного объяснения: привязка сработавшего правила к конкретным значениям параметров, вызвавшим инцидент (сбор `triggerFactors`).

## 3. Область: Интеграция и Хранение данных
*Ответственный: Глеб
Цель: Обеспечить надежное хранение временных рядов, API для клиентов и реактивную маршрутизацию сообщений.*

### Feature Set 3.1: Работа с time-series данными (jOOQ & PostgreSQL)
*   **F.3.1.1** Асинхронная потоковая запись (batch insert) сгенерированной телеметрии в таблицу `telemetry_log`.
*   **F.3.1.2** Извлечение исторических срезов телеметрии для первичной загрузки графиков (с фильтрацией по времени и кауперу).
*   **F.3.1.3** Сохранение истории сгенерированных рекомендаций и фиксация действий оператора.

### Feature Set 3.2: REST API и Контракты
*   **F.3.2.1** Отдача справочника текущих состояний кауперов (эндпоинт `GET /api/v1/cowpers`).
*   **F.3.2.2** Реализация эндпоинта принятия рекомендации оператором (`POST /api/v1/recommendations/{id}/apply`).
*   **F.3.2.3** Автоматическая генерация и отдача OpenAPI (Swagger) спецификации для синхронизации с фронтендом.
*   **F.3.2.4** Расширение схемы `Recommendation` в OpenAPI: добавление объектов `expectedEffect` (напр., `{ "tempDelta": +15, "gasDelta": -50 }`) и `reasoning` (массив триггеров).
*   **F.3.2.5** Реализация эндпоинта `GET /api/v1/system/status` для получения текущего состояния экспертного ядра (`ACTIVE` / `INSUFFICIENT_DATA`).

### Feature Set 3.3: Потоковая передача данных (WebSockets/STOMP)
*   **F.3.3.1** Настройка Message Broker и трансляция новой точки телеметрии в сокет `/topic/telemetry`.
*   **F.3.3.2** Мгновенная маршрутизация сгенерированной рекомендации (алерта) из экспертного ядра Вики в сокет `/topic/recommendations`.
*   **F.3.3.3** Настройка системного топика `/topic/system-status` для мгновенного бродкаста изменения состояния ядра (переход в режим «Недостаточно данных» при обрыве симуляции).

## 4. Область: Интерфейс оператора (Frontend)
*Ответственный: Влад*
*Цель: Предоставить оператору удобный визуальный интерфейс для мониторинга физического процесса и реагирования на инциденты.*

### Feature Set 4.1: Дашборд мониторинга (UI)
*   **F.4.1.1** Отрисовка базового Layout приложения (навигация по кауперам, общие индикаторы статуса).
*   **F.4.1.2** Загрузка исторических данных по REST и построение графиков температуры и расхода с помощью Recharts.
*   **F.4.1.3** Подключение к WebSockets (STOMP-клиент) и динамическое добавление новых точек телеметрии на графики в реальном времени.
*   **F.4.1.4** Обработка режима «Недостаточно данных»: подписка на статус системы, визуальное перекрытие графиков предупреждающим паттерном/баннером и блокировка интерактивных элементов.

### Feature Set 4.2: Управление рекомендациями (UI)
*   **F.4.2.1** Отрисовка всплывающего уведомления (Toast/Notification) при получении нового алерта из сокета.
*   **F.4.2.2** Рендер панели "История рекомендаций" с цветовым кодированием приоритетов и отрисовкой бейджей "Ожидаемый эффект" (например, зеленая плашка `Температура: +15°C`, `Газ: -2%`).
*   **F.4.2.3** Реализация формы реагирования (кнопки "Применить/Отклонить") с отправкой POST-запроса на бэкенд и визуальным обновлением статуса.

### Feature Set 4.3: Панель управления симулятором
*   **F.4.3.1** UI-панель для запуска/остановки симуляции.
*   **F.4.3.2** Интерфейс для инъекции аномалий (например, кнопка «Спровоцировать перегрев купола» для проверки реакции системы).
*   **F.4.2.4** Расширение модалки/карточки алерта блоком "Объяснение": табличный или текстовый вывод параметров, которые спровоцировали данную рекомендацию.
