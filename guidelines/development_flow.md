# Регламент разработки
**Проект:** Интеллектуальная система рекомендаций по управлению воздухонагревателями (ЕвразТехника)
**Команда:** Глеб (Team Lead, Backend/Infra), Вика (Backend/Business Logic), Влад (Frontend/UI)
***
## 1. Методология: Feature-Driven Development (FDD)
Мы не пишем код ради кода. Каждая задача должна представлять собой ценную бизнес-фичу из файла `architecture/fdd_features.md`. 

---
## 2. Стратегия ветвления
В репозитории существует только одна постоянная ветка:
* `main` — **Священная ветка**. Код здесь ВСЕГДА должен компилироваться и проходить тесты. Прямые коммиты (push) в `main` ЗАПРЕЩЕНЫ.

Все новые задачи выполняются в отдельных ветках, которые создаются от актуального `main`.
### Именование веток
Формат: `<тип>/<фича>`
* `feat/...` — для разработки нового функционала.
  * *Пример:* `feat/simulator-math`
  * *Пример:* `feat/overheat-rules`
  * *Пример:* `feat/live-chart`
* `fix/...` — для исправления багов.
  * *Пример:* `fix/ws-connection-drop`
* `docs/...` — для обновления документации (Схемы, OpenAPI).

---
## 3. Правила написания коммитов (Conventional Commits)
Мы используем спецификацию Conventional Commits.
**Формат:** `тип: описание с маленькой буквы в прошедшем времени`

**Типы:**
* `feat:` — новый функционал.
* `fix:` — исправление ошибки.
* `refactor:` — переписывание кода без изменения внешнего поведения.
* `tests:` — добавление или исправление тестов (JUnit / Vitest).
* `chore:` — рутина (настройки сборки, Gradle, Bun, CI).

**Примеры идеальных коммитов:**
> `feat: added exponential growing of temperature`
> `fix: changed color of critical alert to red`
> `test: created tests for jOOQ repositories`
> `chore: changed bun settings`

---
## 4. Жизненный цикл задачи

1. **Синхронизация:** Перед стартом разработчик переключается на `main` и делает `git pull`.
2. **Ветка:** Создает новую ветку (`git checkout -b feat/oxygen-rule`).
3. **Разработка:** Пишет код. **Обязательное условие:** новый код бизнес-логики должен покрываться тестами (JUnit 5 + Mockito для бэкенда).
4. **Локальная проверка:** 
   * Для бэкенда: запустить `./gradlew build` (проверит компиляцию и тесты).
   * Для фронтенда: запустить `bun run tsc -b` (проверит типы TS) и `bun run lint`.
1. **Pull Request (PR):** Разработчик пушит ветку в GitHub и открывает Pull Request в `main`.
	1. При необходимости можно использовать вложенные PR для реализации нескольких фич сразу. Проверяются такие проще.

---
## 5. Code Review и GitHub Actions (CI)
Pull Request не может быть слит (merged) в `main`, пока не выполнены два условия:
### 1. Проверка CI/CD
В репозитории настроено два пайплайна. Если изменен код в папке `backend/`, поднимется Testcontainers и прогоняет все миграции и тесты. Если изменен `frontend/`, соберется Vite.

*Если CI упал — сливать PR нельзя. Автор ветки обязан починить тесты.*
### 2. Одобрение человека (Approve)
Для слияния требуется минимум **1 аппрув** от другого члена команды:
* Код Влада проверяет Глеб.
* Код Вики проверяет Глеб.
* Код Глеба по БД и инфраструктуре могут смотреть Вика или Влад для общего понимания.

*PR обязательно должен быть проверен тим-лидом (Глеб) перед слиянием. *

В комментариях к PR мы не токсичим. Пишем аргументированно: *"Здесь лучше использовать Stream API вместо for-цикла, потому что..."*.

## 6. Базы данных и Миграции (Важно!)
Мы используем **Flyway**.
1. ЗАПРЕЩЕНО изменять уже примененные миграции (например, `V1__init_schema.sql`), если они уже слиты в `main`. 
2. Если нужно добавить колонку, создается новый файл (например, `V3__add_operator_id_to_actions.sql`), который описывает изменение (`ALTER TABLE ...`).
